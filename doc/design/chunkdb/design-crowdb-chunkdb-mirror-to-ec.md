# CROWDB - Design: Mirror-to-EC Conversion and Chunk Tasks

This document defines synchronous small-write EC conversion and the persistent
chunkdb task framework used for recovery and background conversion.

Depends on: [chunkdb](design-crowdb-chunkdb.md),
[chunkdb RPC](design-crowdb-chunkdb-rpc.md), and
[small-object writer](../chunkio/design-crowdb-chunkio-small-object-writer.md).

The read-side producer for repair tasks is the
[chunk object reader](../chunkio/design-crowdb-chunkio-reader.md).

Satisfies: durable space reduction for shared mirror chunks and reusable
crash-recoverable chunk maintenance tasks.

## 1. Scope

Eight adjacent closed one-MiB mirror strips can become one 8+4 EC strip whose
eight data shards preserve the mirror images and whose four parity shards are
generated by isa-l. The small-write client performs this work without rereading
mirrors when memory and I/O are available. A persistent chunkdb task provides
takeover after client failure and supports scanner-created background work.

Incomplete groups remain mirrored. Conversion preserves logical capacity,
`chunk_offset`, `sealed_length`, and the monotonic `next_strip_sequence`.

## 2. Persistent Chunk Tasks

### 2.1 Keys

Each task has one canonical record and at most one runnable or leased index.
Integers use big-endian encoding so index scans retain scheduling order.

```text
ChunkTaskKey       = magic | 0x000D | partition-id:16 | kind:u16 | task-id:16
ReadyChunkTaskKey  = magic | 0x000E | priority-inverse:u8 |
                     eligible-at-ms:u64 | partition-id:16 | kind:u16 |
                     task-id:16
LeasedChunkTaskKey = magic | 0x000F | lease-deadline-ms:u64 |
                     partition-id:16 | kind:u16 | task-id:16
```

The target `ChunkId` is the partition ID for chunk-scoped tasks. Canonical and
index mutations route to the same KV group and are written in one batch. Index
values are empty and rebuildable; the canonical value is task truth.

`task-id` is a deterministic hash of task kind and its deduplication identity.
Mirror conversion uses the first mirror sequence and EC scheme. Its operation
ID is also deterministic, allowing publication retries to identify an already
installed replacement.

`RepairStrip` uses the chunk as partition, the task kind as the dispatch
namespace, and a deterministic task ID derived from strip sequence plus the
sorted failed-segment identities. Its versioned payload contains the chunk ID,
strip sequence, and failed segments. The canonical envelope retains source
revision, estimated full-rebuild I/O bytes, retry state, claim generation, and
the deterministic publication operation ID. Other task types keep their own
payload schema while sharing the envelope, indexes, leases, and transitions.

### 2.2 Value and Handler Dispatch

`ChunkTaskValue` is a verified, versioned FlatBuffer envelope containing stable
identity, kind and kind version, state, priority, revision, source revision,
retry eligibility, attempt budget, queue-cost estimate, claim owner and
generation, lease deadline, bounded error detail, and an opaque typed payload.

States are `Pending`, `Running`, `RetryWait`, `Completed`, `Failed`, and
`Cancelled`. `TaskHandler` dispatch is keyed by kind and checks the payload
version before execution. New task kinds can therefore add their own payload
without changing the scheduler. Replica repair, EC rebuild, orphan cleanup,
and placement verification can use the same envelope.

### 2.3 Claim and Recovery

`TaskManager` admits deterministic tasks, claims ready records, renews leases,
and persists complete, retry, or failure outcomes. `TaskScanner` wakes on
admission and also performs a periodic safety scan. It first requeues expired
leases, then claims no more ready tasks than `TaskExecutor` has available
slots. The executor heartbeats while a handler runs.

The configured concurrency is a fixed upper bound. Retry eligibility and lease
deadlines schedule work; elapsed idle time does not scale worker count.
Conversion and repair handlers also enforce independent local concurrency
semaphores. Repair has the highest ready priority because it restores data
redundancy, while conversion only reclaims space.

### 2.4 Read Repair Admission and Execution

Readers durably add exact failed segment identities to
`ChunkStrip.unavailable_segments`. A bounded rotating metadata scan admits one
task per strip and failure set. An existing pending, running, or retry-wait
task deduplicates admission. A terminal task is revived at a higher revision
when its marker remains, preventing a stale completion or failure from
suppressing necessary repair.

`RepairStripTaskHandler` re-queries current metadata and treats the marker as
authority. It reads one full healthy mirror or full EC shards, records any new
I/O failures before retrying, reconstructs unavailable shards, and allocates
replacement segments excluding every disk already used by the strip. Normal
placement also excludes survivor nodes; a separate disabled-by-default test
escape hatch may relax only node anti-affinity, never same-disk exclusion.

Each replacement is fully written and fsynced before exact revision-and-range
fenced publication. The publication removes repaired markers and adds retired
segments to the normal layout-validity cleanup intent. A changed layout causes
re-query and retry. Repair tasks have unlimited attempts and use delayed retry
rather than tight polling when memory, placement, parity, or I/O is temporarily
unavailable.

## 3. Foreground Conversion

Each small-write pipeline retains an immutable image after a mirror strip is
closed and synchronously updates four persistent parity buffers. The eighth
update completes parity without rereading the preceding seven mirrors.

The data and parity buffers reserve one complete EC group's memory atomically.
Reservation is nonblocking because conversion is an optimization after mirror
durability: if the group cannot fit, the client releases the image and lets the
chunkdb scanner convert later. A group is not started when the current chunk
cannot contain enough remaining full strips to finish it.

A pipeline holding a partial group is not a scale-in candidate. Scale-in first
requires every queue to be empty and every pipeline to be non-busy, then removes
an individual pipeline that does not own partial conversion state. Queue bytes
and object count remain the only scale-out inputs.

After shard eight, the client:

1. prepares a durable `MirrorToEc` task and tentative EC placement;
2. writes the retained eight data shards and four parity shards in parallel;
3. fsyncs every target segment;
4. completes the task through fenced range replacement.

A fast-path error does not revoke acknowledged mirror writes. The durable task
remains available for takeover after its client claim expires.

## 4. Background Conversion

`ConversionCoordinator` scans chunk metadata in bounded rotating pages and
admits complete compatible mirror groups. A group must have equal nonzero unit
geometry, contiguous offsets, and an immutable closed boundary. Sealed chunks
also obey the configured age policy; manual single-chunk triggers bypass age
and count policy but not geometry, closure, or chunk-state checks.

`MirrorToEcTaskHandler` reads one healthy replica for each mirror, falling back
across replicas on routing or DiskIO errors. It generates parity, writes and
fsyncs all replacement shards, and invokes the same fenced publication used by
the client. Disk-to-DiskIO routes are atomically published and periodically
refreshed from hardware and service-registry state.

Automatic scans leave incomplete tails mirrored and continue across task
failures. Manual single and batch triggers are available through crowdb-rpc and
the `/convert_chunk` and `/convert_all` HTTP endpoints.

## 5. Publication and Cleanup

`allocate_conversion_strip` creates a tentative EC strip with the first
mirror's offset and sequence and the old range's total capacity and sealed
length. No task phase makes that strip readable.

`replace_chunk_strip_range` validates the expected revision and exact old
range. Its KV transaction commits replacement segments, publishes the EC strip,
and records retired mirror segments as one atomic metadata change. Retired
segments remain allocated for the layout-validity grace period; reconciliation
then frees only segments absent from the current layout.

On a definite pre-publication failure, the task first clears its durable
replacement reference. DiskDB's tentative-block scanner reclaims the now
unreferenced allocation. An ambiguous KV response retains the allocation until
recovery determines whether its checkpoint or publication committed.

## 6. Crash Correctness

- **C1 — Layout authority:** readers use only committed `Chunk.strips`; task
  state and tentative blocks never select readable data.
- **C2 — Mirror preservation:** every mirror remains referenced until every EC
  shard is written and fsynced.
- **C3 — Atomic visibility:** fenced range replacement is the only EC
  publication point.
- **C4 — Ambiguity retains data:** an ambiguous checkpoint or publication never
  frees a possibly referenced replacement.
- **C5 — Replayable retirement:** replacement and cleanup intent commit
  together, and cleanup uses set difference against the current layout.
- **C6 — Duplicate safety:** deterministic identity and revision/range fencing
  permit at most one layout publication even if claims overlap.
- **C7 — Append independence:** replacement preserves capacity and
  `next_strip_sequence`, so later appends cannot duplicate or reorder strips.

A takeover rewrites all shards and fsyncs them; it does not trust partial-write
progress. If publication is already visible anywhere in the current layout,
the handler treats the operation as installed. If allocation succeeded but no
task checkpoint references it, the allocation remains tentative garbage and is
eventually reclaimed by DiskDB. This can temporarily consume space but cannot
make corrupt data visible.

## 7. Policy and Observability

`ConversionConfig` defaults to disabled automatic scanning, 8+4 EC, one-hour
minimum seal age, eight mirror strips, four concurrent handlers, 50 MiB/s
background I/O, a 30-second scan interval, and a 30-second task lease.

The bandwidth limiter atomically reserves read-plus-write byte time and permits
one conversion-group burst. Time controls only background bandwidth and retry
or lease scheduling; it does not control small-write pipeline scale-in/out.

`ConversionMetrics` exposes attempts started/completed/failed, bytes read and
written, retired mirror segments, active handlers, and peak active handlers.
`GET /conversion_metrics` returns a nonblocking snapshot.

`RepairConfig` defaults to enabled, four concurrent handlers, a 64-MiB shared
full-shard memory budget, and a one-second marker scan. The memory semaphore is
reserved before shard reads. A repair larger than the configured budget stays
durably retryable. `RepairMetrics` exposes admissions, attempts, repaired
segments and bytes, active handlers, and current/limit/peak memory through
`GET /repair_metrics`.

## 8. Test Contract

Core coverage uses real KV, chunkdb, diskdb, DiskIO, and routed clients. It
verifies foreground no-reread conversion, data and parity bytes, missing-shard
decode, active-prefix append, client-I/O failure takeover, manual and automatic
triggers, multiple groups plus mirror tail, bounded task dispatch, cleanup
reconciliation, and process crash/restart recovery. Mock-based tests remain
auxiliary for deterministic error injection and unit-level queue behavior.

Read-repair coverage additionally verifies same-offset partial EC recovery,
minimum surviving-shard reads, mirror fallback and total loss, exact partial
ranges, stream termination, incomplete-parity behavior, durable marker
admission across process restart, full-shard replacement, task revival,
memory/metrics bounds, and continued writes to an active chunk whose revision
was advanced by a reader.
